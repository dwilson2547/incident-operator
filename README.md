# incident-operator

Turns Alertmanager alerts into tracked incidents and has a small local LLM (through gpu-scheduler) triage each one.
The model picks and explains; code decides what can run. Design: [`docs/design.md`](docs/design.md).

**Status: phase 3 (approved fixes), built 2026-11-01.** It changes the cluster only through a fix a signed-in human
approved, run by a separate executor with rights generated from the committed fix files. Otherwise the only objects
it creates are short read-only probe Jobs. Phase 4 (`auto` for fixes with a record) is next (design §14).

## Fixes (phase 3)

A fix is an operation with `mutating: true` (`files/operations/`), offered by a runbook's `operations` list (design
§7, `fixes.py`, `executor.py`):

```yaml
operations: [tower-load, {restart-csi-nfs-node: {autonomy: approve}}]    # in the runbook; raises the op's default
```

1. **Proposal:** the remediation step may name one of the runbook's fixes, or `none` (the JSON schema allows only
   those). Parameters come from the alert and target, never the model.
2. **Autonomy** `suggest`: the page and email show the `kubectl` equivalent; nothing runs from here. `approve`: the
   page shows Approve/Reject (signed-in users only) and the email says it's waiting.
3. **Approve → pre-checks:** the controller runs the fix's `pre` checks fresh (e.g. a new `nfs-dstate` probe) and
   its `limits` (per target and overall). A failed check or limit refuses the fix; so does a fix file that changed
   since the proposal.
4. **Executor:** its own Deployment and ServiceAccount takes the `ready` run, re-reads the operation from its own copy
   of the files, checks the parameters again, and performs the verb: `DeletePods` (label selector, optional node,
   refuses more than `maxPods`) or `CreateJobFrom` (a CronJob's job template, like `kubectl create job --from`).
   Its Roles are generated by the chart: for each fix, in each namespace it lists, exactly what its verb needs.
5. **Post-checks** after `settle` seconds: `succeeded` or `post_failed`. Each outcome is mailed. The Runbooks page
   lists each fix's record (proposed, ran, passed post-checks, last failure).

| Fix | Verb | Pre | Post (after 120 s) | Autonomy |
|---|---|---|---|---|
| `restart-csi-nfs-node` | delete the node's `csi-nfs-node` pod | stuck `mount.nfs` older than 10 min, children of the CSI pod | no stuck `mount.nfs`; DaemonSet fully available | `suggest`, `approve` in `nfs-client-wedge` |
| `rerun-backup-job` | a Job from the backup CronJob (postgres, offsite-backup, secrets-backup) | no run active; not suspended | (90 s) a Job of the CronJob started; the backup alerts judge the result | `suggest` in `backup-job-failed` |

Checks are `<path> <op> <literal>` on a read-only operation's structured result (`==`, `!=`, `>`, `>=`, `<`, `<=`;
numbers, `true`, `false`, `null`, `"text"`; strict, so `1` is not `true`).

**Sign-in:** with `ui.oidc.issuer` set, every page needs an authentik sign-in (gpu-scheduler's `oidc.py`), and who
may sign in is the `incident-operator-admins` group (cluster-config `authentik/blueprints/incident-operator.yaml`).
Without it the page is open on the LAN and fixes can't be approved (`ALLOW_ANONYMOUS_DECISIONS=1` is for local runs).
`ui.tlsSecretName` publishes the page (`ui.host` a `*.danwils.com` name; DNS, certificate and edge limits follow from
the Ingress, cluster-config "Public vs internal ingress"); the chart refuses that without `ui.oidc.issuer`.

## Runbooks (phase 2a)

An alert that matches a runbook (`helm/incident-operator/files/runbooks/*.md`) gets a two-session triage instead of
the generic one below (design §6):
1. **Target** from the alert's labels (or `instance` → node by IP), never from the model.
2. **Precursors:** the runbook's read-only operations (`files/operations/*.yaml`) run in code first.
3. **Investigation:** up to 3 JSON turns. Each either asks for operations from the runbook's menu (they run and the
   results go back) or finishes with findings (what failed, where, confidence, summary). gpu-scheduler holds the reply
   to a JSON schema (constrained decoding); the last turn's schema only allows finishing.
4. **Remediation:** one call that sees the findings and the runbook's `## Remediation`, never raw logs. Its advice
   (suggestion, why, will it fix itself, escalate) is the email and the page's answer.

| Runbook | Alerts | Target |
|---|---|---|
| `pod-crashloop` | `KubePodCrashLooping` | the pod |
| `backup-job-failed` | `PostgresBackupJobFailed`, `OffsiteBackupJobFailed`, `SecretsBackupJobFailed` | the Job |
| `nfs-client-wedge` | `NodeLoadHighCPUIdle` (new, cluster-config) | the node |
| `scraper-failures` | `ScrapeJobStale`, `ScrapeJobSuspended` | the ScrapeJob |

Operation kinds: `k8s-summary` (pod/Job/workload/node status, events, logs), `k8s-get` (fields of any object, e.g. a
ScrapeJob), `k8s-events` (by reason, node or object), `k8s-logs`, `promql`, `promql-range` (downsampled),
`alert-objects` (the generic phase-1 evidence), and `probe`.

**Probes** (phase 2b, `probes.py`) run on the target node as a short Job in this namespace: pinned with `nodeName`,
`hostPID` so `/proc` shows the node's tasks, and nothing else (no volumes, no service-account token, non-root, no
capabilities, read-only root, 60 s deadline); the operator reads its one line of JSON and deletes the Job. Probes are
named code in the image: an operation file picks one, it can't supply a command. Never a mount, so a probe can't wedge
a node. `nfs-dstate`: D-state tasks by command, stuck `mount.nfs` (count, older than 10 min, oldest, their parents),
stuck `nfsplugin` threads, the NFSv4 state manager thread. Run on all four nodes 2026-11-01: ~20 s each. Parameters come from `target.*`, `alertLabel:<name>` or
`result:<operation>.<path>`, and are refused unless they look like plain names. No `logql`: Loki holds only object
store audit logs today. Files are validated on load (references, parameter sources, the design's size limits); a bad
file is rejected and its last good version stays live, also across a restart (each file that loads is saved in
Postgres, `library_last_good`). The **Runbooks** page lists what loaded, what was rejected
and why, and how often each runbook matched.

**Replay** a stored incident against edited runbooks or another model (results come from what was stored, never
the live cluster):

```bash
DATABASE_URL=... GPU_SCHEDULER_URL=... GPU_SCHEDULER_TOKEN=... .venv/bin/python -m incident_operator replay 12 15 --model gemma4-26b-a4b
```

`--live` runs the checks against the cluster as it is now instead (`KUBE_API_URL` from `kubectl proxy`,
`PROMETHEUS_URL`; probes don't run), to try a changed operation on an incident whose objects still exist. Replay
never proposes or runs a fix.

## Without a runbook (phase 1)

1. **Intake:** Alertmanager posts the alerts it also mails (critical, plus the listed warnings) to the webhook. One
   incident per alert fingerprint: re-sends update it, a resolve closes it, the next firing opens a new one.
2. **Evidence**, collected by code, read-only, before any model call: for whatever the alert's labels name, a pod's
   status, events and log tail (and the previous container's after a restart), a Job's status and its newest pod, a
   workload's status and events, a node's conditions (node-exporter's `instance` IP is mapped to the node). Capped per
   item and per incident (14k characters), so a small model's prompt stays around 1.5–5k tokens.
3. **Triage:** one call to gpu-scheduler with the system prompt, the environment primer
   (`helm/incident-operator/files/primer.md`, mounted, read on every call) and the evidence. `qwen35-9b` on the
   3080, with `gemma4-26b-a4b` on the Mac as fallback after 60 s. Every prompt is stored as sent.
4. **Brakes** against a noisy alert, before any evidence or model call:
   - **Repeats:** each incident gets a problem key: its labels, with pod and Job names cut to their stem
     (`offsite-objects-29886270-4rg6q` → `offsite-objects`) and per-occurrence labels dropped. If the same key was
     triaged in the last 6 h, the incident is a `repeat` of that one: no model call, no email, shown folded under it.
     Covers flapping alerts and failures that recur under new names (CronJob runs, recreated pods).
   - **Hourly cap:** at most 12 triage calls an hour; the rest wait, oldest first. One that resolved over an hour
     before its turn is `skipped`, so a storm doesn't become hours of late emails.
5. **Email**, one per incident, with the answer, which model and machine answered, the evidence list and a link.
6. **Page** at http://incident-operator.cluster.local (LAN): incidents, each one's answer, evidence and exact prompt,
   and "needs a runbook": alerts that fired with no runbook (all of them, in phase 1).

Checked end to end on 2026-11-01 against the real cluster and gpu-scheduler: two real failed Jobs (an OOMKilled
`rclone` backup, a parts-direct scraper that timed out) were triaged in 25 s by `qwen35-9b` on the 3080; both
answers found the right container, exit code and log line.

## Layout

- `src/incident_operator/db.py`: incidents, evidence, model turns (schema created on start).
- `src/incident_operator/evidence.py`: the read-only Kubernetes reads and the budget.
- `src/incident_operator/triage.py`: the engine (idempotent passes: new → submit, poll, notify), the phase-1 prompt
  and the gpu-scheduler client.
- `src/incident_operator/library.py`, `ops.py`, `investigate.py`, `replay.py`: runbook/operation loading, running
  read-only operations, the two runbook sessions, replay.
- `src/incident_operator/fixes.py`, `executor.py`: fixes from proposal to post-check; the executor's verbs.
- `src/incident_operator/oidc.py`: authentik sign-in for the page (from gpu-scheduler).
- `src/incident_operator/notify.py`: SMTP email (same settings as scrape-job-manager).
- `src/incident_operator/app.py` + `static/index.html`: the webhook (port 8081, in-cluster Service only, no Ingress,
  so the LAN can't inject alerts) and the page (8080).
- `helm/incident-operator/`: Deployment, the read-only ClusterRole, Services, LAN Ingress, the primer ConfigMap, and
  the executor Deployment with its generated Roles.
- `scripts/create-secrets.sh`, `scripts/setup-argo-access.sh`: one-time setup (they generate secrets and print none).

## Configuration

| Env | |
|---|---|
| `DATABASE_URL` | Postgres (Secret `incident-operator-db`) |
| `GPU_SCHEDULER_URL`, `GPU_SCHEDULER_TOKEN` | gpu-scheduler API and this client's token |
| `TRIAGE_MODEL`, `TRIAGE_FALLBACK`, `TRIAGE_FALLBACK_AFTER_SECONDS` | `qwen35-9b`, `gemma4-26b-a4b`, 60 |
| `TRIAGE_DEADLINE_SECONDS`, `TRIAGE_MAX_NEW_TOKENS` | 900, 1024 |
| `TRIAGE_REPEAT_WINDOW_SECONDS`, `TRIAGE_MAX_PER_HOUR`, `TRIAGE_SKIP_RESOLVED_AFTER_SECONDS` | 21600, 12, 3600 |
| `PRIMER_PATH` | the primer file (the chart mounts it at `/etc/incident-operator/primer.md`) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TO`, `PUBLIC_URL` | email; off unless host, from and to are set |
| `UI_PORT`, `WEBHOOK_PORT` | 8080, 8081 |
| `RUNBOOKS_DIR`, `OPERATIONS_DIR`, `PROMETHEUS_URL` | the mounted ConfigMaps; Prometheus for `promql` operations |
| `TRIAGE_INVESTIGATE_MAX_NEW_TOKENS` | 768, per investigation/remediation turn |
| `KUBE_API_URL` | local runs: e.g. `kubectl proxy` at `http://127.0.0.1:8001`; in the cluster the service account is used |
| `EVIDENCE=off` | skip the Kubernetes reads |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | authentik sign-in for the page; `PUBLIC_URL` is the callback's base |
| `ALLOW_ANONYMOUS_DECISIONS=1` | local runs only: approve without sign-in (ignored when `OIDC_ISSUER` is set) |

## Develop

```bash
python3 -m venv .venv && .venv/bin/pip install -e '.[test]'
docker run -d --name io-pg -e POSTGRES_PASSWORD=dev -p 127.0.0.1:55444:5432 postgres:17
PGPASSWORD=dev INCIDENT_OPERATOR_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55444/postgres .venv/bin/pytest -q
./start.sh          # the service on :8090 (UI) / :8091 (webhook), evidence and email off
./kill.sh
```

The test fixture refuses a database with tables other than its own (another project's local Postgres answered on the
same port once).

## Release

Pushing to `main` runs the tests and publishes `dwilson2547/incident-operator:sha-<12>` (`.github/workflows/ci.yml`;
chart, primer and doc changes don't build). To deploy: set `image.tag` in `values-prod.yaml` and push; Argo app
`incident-operator` rolls it out. A primer change is a chart change: it reaches the running pod within a minute.
